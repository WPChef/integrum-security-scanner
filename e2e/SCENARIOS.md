# E2E Test Scenarios

Сценарии end-to-end тестирования плагина File Security Scanner через mock-сервер.

Каждый сценарий независим, может запускаться в любом порядке и не требует внешних сервисов — только `e2e/mock/server.php`.

## Sandbox

Окружение: DDEV (`https://llar-imunify.ddev.site`), mock-сервер на `127.0.0.1:9000`.

Mock включается опцией `security_scanner_e2e_mock` (mu-plugin перенаправляет вызовы
LLAR/Scanner API на mock-сервер) — правки `wp-config.php` не нужны:

```
curl -sk "https://llar-imunify.ddev.site/test-helper.php?action=enable-mock"   # включить mock
curl -sk "https://llar-imunify.ddev.site/test-helper.php?action=disable-mock"  # вернуть реальный API
curl -s -X POST http://127.0.0.1:9000/reset                                    # сброс состояния mock
```

Прочие действия `test-helper.php`: `cleanup` (сброс настроек/транзиентов плагина),
`import-has-key` / `import-no-key` (дампы), `create-test-dir` (тест-директория
`e2e-test-scan-dir` с 3 файлами), `get-site-key`, `set-key-<key>`, `reset-mock`.

Состояние mock хранится в `e2e/mock/state.json` — его можно удалить вручную для полного сброса.

Автоматизированные сценарии (S1, S2, S4, S6, S16–S23) живут в `e2e/tests/imunify.spec.ts`
(Playwright); остальные описаны для ручной проверки.

## S1. Happy path — чистый сайт, нет заражений

**Цель**: проверить полный цикл от регистрации до результатов, все файлы clean.

**Mock-конфигурация**: `CyclicVerdictStrategy` (по умолчанию).

**Шаги**:

1. Открыть страницу плагина (`/wp-admin/admin.php?page=security-scanner`).
2. Ввести email, нажать «Register» (`POST /imunify/site`).
3. **Проверка**: notice «Site registered. Plan: free.», отображается Site ID.
4. В дереве директорий всё по умолчанию: корень «/» (root), wp-admin, wp-includes,
   wp-content отмечены; маски пустые. Секция «Files to scan» уже показывает превью
   дерева файлов до запуска скана.
5. Нажать «Start Scan» (`POST /api/v1/scan/start`).
6. **Проверка**: появляется прогресс-бар, статус «processing».
7. Дождаться завершения (~16 секунд = 4 поллинга по 4 секунды).
8. **Проверка**: прогресс доходит до 100%, статус → «completed».
9. **Проверка**: дерево файлов отображается, чекбокс «Show suspicious only» активен.
10. Снять чекбокс — **проверка**: видны все файлы, включая clean.
11. Поставить чекбокс — **проверка**: clean-файлы скрыты, видны только malicious/suspicious.

**Ожидаемые вердикты** (по умолчанию, `file_index % 3`):
- `file_index % 3 == 1` → malicious (EICAR_TEST_FILE)
- `file_index % 3 == 2` → suspicious (OBFUSCATED_EVAL)
- `file_index % 3 == 0` → clean

**Файлы для проверки**: любые `.php`-файлы в корне WordPress (например `index.php`, `wp-config.php`, `wp-load.php`).

## S2. Повторная регистрация — уже зарегистрированный домен

**Цель**: плагин корректно обрабатывает HTTP 400 от LLAR API.

**Pre-condition**: сайт уже зарегистрирован (выполнен S1 или прямой `POST /imunify/site`).

**Шаги**:

1. Открыть страницу плагина.
2. Отправить форму ключа повторно (кнопка «Register»/«Save key»).
3. **Проверка**: красный notice «This site is already registered. Try retrieving a new key or contact support.»
4. **Проверка**: плагин не упал, форма доступна для повторного действия.
5. **Проверка**: в `wp-content/debug.log` есть запись `site registration bad response` с `code: 400`.

## S3. Невалидный email

**Цель**: валидация на клиентской и серверной стороне.

**Шаги**:

1. Открыть страницу плагина.
2. Ввести `not-an-email` в поле email.
3. Нажать «Register».
4. **Проверка**: HTML5-валидация блокирует отправку (атрибут `type="email"`).
5. Обойти валидацию (например через `curl` напрямую на `/imunify/site` с `"email":"bad"`).
6. **Проверка**: mock возвращает 400, плагин показывает «Please provide a valid email address.»

## S4. Запуск скана без ключа

**Цель**: плагин блокирует сканирование при отсутствии `site_key`.

**Pre-condition**: `site_key` отсутствует (сбросить через `wp option delete security_scanner_credentials`).

**Шаги**:

1. Открыть страницу плагина.
2. **Проверка**: секция «Scan area» полупрозрачна и не кликабельна (`pointer-events-none opacity-60`), кнопка «Start Scan» имеет атрибут `disabled`.
3. **Проверка**: в шапке страницы бейдж «Not connected».
4. Попытка отправить форму вручную (например `curl`).
5. **Проверка**: плагин возвращает admin notice «The site key is missing or was rejected. Use the "Get site key" form above to obtain a new key, then start the scan again.»

## S5. Маски файлов — include/exclude

**Цель**: проверить, что `FileCollector` правильно фильтрует файлы для сканирования.

**Pre-condition**: сайт зарегистрирован, ключ получен.

**Шаги**:

1. В дереве директорий оставить отмечённой только `wp-content` (снять галочку
   с корня «/» — каскадом снимутся все подпапки, затем отметить `wp-content`).
2. Include: `*.php`
3. Exclude: `*/cache/*, */vendor/*`
4. Нажать «Start Scan».
5. **Проверка (через debug log)**: в манифесте, отправленном на `/api/v1/scan/start`, нет файлов из `cache/` и `vendor/`.
6. **Проверка (через UI)**: по завершении скана дерево содержит только файлы из `wp-content/`, без `cache/` и `vendor/`.

## S6. Неверный site_key — ошибка аутентификации

**Цель**: плагин корректно обрабатывает 401 от File Security Scanner.

**Pre-condition**: в `wp_options` подменён `site_key` на заведомо невалидный:
```
wp option patch update security_scanner_credentials site_key 'deadbeef'
```

**Шаги**:

1. Нажать «Start Scan».
2. **Проверка**: сообщение «The site key is missing or was rejected. Use the "Get site key" form above to obtain a new key, then start the scan again.»
3. Ввести рабочий email и сохранить ключ через форму (кнопка «Save key»).
4. **Проверка**: ключ обновлён, кнопка «Start Scan» активна.
5. Запустить скан повторно — **проверка**: скан запускается успешно.

## S7. Сетевой сбой при старте скана

**Цель**: плагин не падает при недоступности Imunify API.

**Pre-condition**: mock-сервер **остановлен** (`kill %1` если запущен через `&`).

**Шаги**:

1. Нажать «Start Scan».
2. **Проверка**: сообщение «Could not start the scan. Please try again in a moment.»
3. Запустить mock-сервер заново.
4. Нажать «Start Scan» снова.
5. **Проверка**: скан запускается, прогресс-бар появляется.

---

## S8. Сетевой сбой при поллинге → эскалация в failed

**Цель**: проверить механизм эскалации после 5 последовательных сбоев поллинга (`MAX_STATUS_FAILURES = 5`).

**Pre-condition**: скан запущен (выполнен шаг до появления прогресс-бара), затем mock-сервер остановлен.

**Шаги**:

1. Дождаться ~20 секунд (5 поллингов × 4 секунды).
2. **Проверка**: статус меняется на «failed», прогресс-бар останавливается.
3. **Проверка**: в `debug.log` есть 5 записей `status poll failed` с инкрементирующимся `failures`.
4. Запустить mock-сервер заново.
5. Нажать «Start Scan» (новый скан).
6. **Проверка**: счётчик сбоев сброшен, скан идёт нормально.

## S9. Refresh страницы во время скана

**Цель**: перезагрузка страницы не возобновляет скан молча — UI возвращается в idle.

**Pre-condition**: скан запущен, идёт поллинг.

**Шаги**:

1. Обновить страницу (`Cmd+R` / `F5`).
2. **Проверка**: секция прогресса скрыта, скрытый `.llar-job-id` пуст — poller не
   стартует (job id берётся только из one-shot transient `security_scanner_started_job`,
   а не из `security_scanner_active_job`).
3. **Проверка**: кнопка «Start Scan» снова доступна.
4. **Проверка**: сам скан продолжает выполняться на сервере (job store); вкладка,
   которая не обновлялась, продолжает поллинг до завершения.

Автотест: S19 (`e2e/tests/imunify.spec.ts`).

## S10. Capability check — доступ только для админа

**Цель**: non-admin пользователи не видят страницу плагина.

**Pre-condition**: создан пользователь с ролью Editor (без `manage_options`).

**Шаги**:

1. Залогиниться под Editor.
2. **Проверка**: пункт меню «File Security» отсутствует.
3. Перейти по прямому URL `/wp-admin/admin.php?page=security-scanner`.
4. **Проверка**: страница не отображается (или стандартное сообщение WordPress «Sorry, you are not allowed to access this page»).
5. Попытка отправить POST напрямую через `curl` с куками Editor.
6. **Проверка**: nonce-проверка или capability-проверка возвращает ошибку.

## S11. CSRF — запрос без nonce

**Цель**: формы и AJAX защищены от CSRF.

**Шаги**:

1. Сформировать POST-запрос к `/wp-admin/admin.php?page=security-scanner` без поля `_wpnonce`.
2. **Проверка**: WordPress возвращает «The link you followed has expired.» или 403.
3. Сформировать AJAX-запрос к `admin-ajax.php` без nonce.
4. **Проверка**: ответ `wp_send_json_error` с 403.

## S12. Несколько сканов подряд

**Цель**: второй скан не ломает состояние первого.

**Шаги**:

1. Запустить первый скан (любые директории).
2. Дождаться завершения.
3. Изменить выбор в дереве директорий (например, оставить только `wp-admin`).
4. Запустить второй скан.
5. **Проверка**: прогресс-бар обновляется для нового job_id.
6. **Проверка**: результаты второго скана не содержат файлов из первого (если директории не пересекаются).
7. **Проверка**: `GET /debug` на mock-сервере показывает два завершённых job.

## S13. Concurrent requests — два поллинга в одном окне

**Цель**: двойной вызов `fetchJSON` из JS не ломает состояние.

**Шаги**:

1. Запустить скан.
2. В консоли браузера дважды быстро вызвать `fetch(...)` на `security_scanner_status`.
3. **Проверка**: оба ответа возвращают корректный `progress_pct`, статус консистентен.
4. **Проверка**: AJAX-запросы не создают дублирующих job в mock-сервере.

## S14. Oversized file — пропуск больших файлов

**Цель**: файлы > 2 МБ не попадают в манифест.

**Pre-condition**: в корне WordPress создан файл `test-big.dat` размером 3 МБ.

**Шаги**:

1. Include: `*`
2. Запустить скан.
3. **Проверка (через debug log или прямой `/debug` mock-сервера)**: в манифесте отсутствует `test-big.dat`.
4. **Проверка**: файлы > 2 МБ не вызывают ошибок, скан завершается нормально.

## S15. File tree rendering — вложенные папки

**Цель**: дерево файлов правильно группирует файлы по директориям.

**Pre-condition**: в `wp-content/` создана структура `plugins/test-plugin/test.php` и `plugins/test-plugin/readme.txt`.

**Шаги**:

1. В дереве директорий оставить отмечённой только `wp-content`, include: `*`.
2. Запустить скан, дождаться завершения.
3. **Проверка**: дерево показывает:
   ```
   wp-content/
   ├── plugins/
   │   └── test-plugin/
   │       ├── test.php
   │       └── readme.txt
   ```
4. **Проверка**: клик по ▸ сворачивает/разворачивает папку.
5. **Проверка**: если `test.php` — malicious, папка `test-plugin/` раскрыта и подсвечена красным.
6. **Проверка**: если в папке все файлы clean, она свёрнута, имя обычного цвета.

## S17. Настройки формы скана сохраняются между перезагрузками

**Цель**: выбор директорий (флаги дерева) и масок переживает reload (persist в `security_scanner_settings`).

**Шаги**:

1. Импортировать дамп `has-key`, создать тест-директорию, открыть страницу плагина.
2. Снять галочку с корня «/» (каскадом снимутся все подпапки), отметить только `e2e-test`;
   маски: include `*.php`, exclude `*/cache/*`.
3. Запустить скан (настройки сохраняются при сабмите формы — до старта job).
4. Перегрузить страницу.
5. **Проверка**: root, wp-admin, wp-includes без галочек (дерево восстановлено из
   сохранённых флагов `tree`), маски на месте.

**Цель**: reload в процессе скана не подхватывает job молча (см. S9).

**Шаги**:

2. Перегрузить страницу.

## S20. Деактивация плагина — страница админки исчезает, сайт жив

**Цель**: деактивация через plugins.php убирает пункт меню и страницу плагина, не ломая сайт.

**Шаги**:

1. Импортировать дамп `has-key` (плагин активен).
2. Открыть `plugins.php`, нажать «Deactivate» в строке плагина.
3. **Проверка**: в строке снова есть действие «Activate».
4. Зайти в `/wp-admin/index.php`.
5. **Проверка**: пункта «File Security» в меню нет.
6. Открыть `/wp-admin/admin.php?page=security-scanner` напрямую.
7. **Проверка**: HTTP 403, «Sorry, you are not allowed to access this page» (меню не зарегистрировано → `wp_die`).
8. Открыть главную страницу сайта.
9. **Проверка**: HTTP 200 — фронт работает, от деактивации нет фатальных последствий.

## S21. Активация плагина — страница возвращается без фатальной ошибки

**Цель**: активация через plugins.php проходит sandbox-скрап главного файла без фатала.

Это регрессионный тест на класс багов, который ломал активацию в проде:
несовпадение сигнатуры конструктора (`Argument #5 ($domain) must be of type string`)
вызывало `PHP Fatal Error` внутри `plugin_sandbox_scrape`, и плагин не активировался.

**Шаги**:

1. Импортировать дамп `has-key`, деактивировать плагин через UI (предусловие).
2. Нажать «Activate» в строке плагина.
3. **Проверка**: в строке появилось действие «Deactivate»; нет инлайн-ошибки «could not be activated because it triggered a fatal error».
4. Зайти на `/wp-admin/index.php`.
5. **Проверка**: пункт «File Security» в меню есть.
6. Открыть страницу плагина.
7. **Проверка**: заголовок и форма скана рендерятся (`.security-scanner h1`).

## S22. Превью дерева файлов до сканирования + дефолтные директории

**Цель**: дерево файлов для сканирования видно сразу при открытии страницы, а не только как результат сканирования; все стандартные директории включены по дефолту.

**Шаги**:

1. Импортировать дамп `has-key`, создать тест-директорию, открыть страницу плагина.
2. **Проверка**: чекбоксы root, wp-admin, wp-includes, wp-content отмечены (до первого сохранения настроек).
3. **Проверка**: секция «Files to scan» видима; после загрузки в дереве есть узлы (папки/файлы), счётчик показывает «N files».
4. Выбрать только `e2e-test` (снять стандартные директории).
5. **Проверка**: превью перерисовалось — ровно 3 файла тест-директории, счётчик «3 files».
6. Ввести include-маску `test-0.php`.
7. **Проверка**: превью сузилось до 1 файла (маски учитываются в превью как в сканировании).

## S23. Дерево директорий — вложенные папки с каскадными чекбоксами

**Цель**: вместо плоского списка чекбоксов — дерево папок; выбор родителя выбирает все подпапки, снятие галочки с подпапки снимает галочку родителя (родитель показывается в промежуточном состоянии «тире»).

**Шаги**:

1. Импортировать дамп `has-key`, открыть страницу плагина.
2. **Проверка**: дерево директорий видимо; root, wp-admin, wp-includes, wp-content отмечены.
3. Раскрыть `wp-content` (ленивая загрузка подпапок через `security_scanner_dirchildren`).
4. Снять галочку с `wp-content/plugins`.
5. **Проверка**: `wp-content` и root — без галочки, в indeterminate-состоянии (частичный выбор); `wp-admin` остаётся отмечен.
6. **Проверка**: скрытый input `security_scanner_tree_off[]` содержит `wp-content/plugins` (явный флаг отправляется формой).
7. Снова отметить `wp-content`.
8. **Проверка**: всё дерево отмечено (включая `wp-content/plugins`), промежуточные состояния сняты, флагов не осталось.

## Как запускать

```sh
# 1. Поднять окружение и mock
ddev start
php -S 127.0.0.1:9000 -t e2e/mock e2e/mock/server.php &

# 2. Включить mock-режим (mu-plugin перенаправит API-вызовы)
curl -sk "https://llar-imunify.ddev.site/test-helper.php?action=enable-mock"

# 3. Сбросить состояние перед тестом
curl -s -X POST http://127.0.0.1:9000/reset

# 4. Выполнить сценарий по шагам (руководствуясь описанием выше)
# или прогнать автотесты:
npx playwright test                # весь сюит (S1–S23)
npx playwright test -g "S23"       # один сценарий

# 5. Проверить состояние mock-сервера
curl -s http://127.0.0.1:9000/debug | python3 -m json.tool

# 6. Вернуть реальный API
curl -sk "https://llar-imunify.ddev.site/test-helper.php?action=disable-mock"
```

## Имей в виду

- Mock-сервер распределяет вердикты циклически по `file_index % 3`. При малом количестве файлов (1-2) какие-то вердикты могут не встретиться.
- Время поллинга — 4 секунды. Сценарий с эскалацией (S8) занимает ~20 секунд.
- `php -S` — однопоточный сервер. Два одновременных запроса встанут в очередь, а не упадут — S13 это не ломает.
- AJAX-запросы через `admin-ajax.php` требуют WordPress-сессию (куки). Тестировать их curl-ом сложно — лучше через Playwright / браузерную консоль.
